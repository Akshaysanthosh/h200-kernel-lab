## Research basis and selection

FlashAttention-3 demonstrates that Hopper's asynchronous data movement and tensor cores can benefit from warp specialization and overlapping independent work: https://tridao.me/publications/flash3/flash3.pdf. Its attention speedups are not GEMM predictions. Twill formulates software-pipeline and warp-specialization scheduling jointly: https://arxiv.org/abs/2512.18134. Neither paper proves a gain on this workload.

The public source supplies a concrete alternative implementation for these ideas: SK2 uses separate producer, tensor-core consumer and sparse-correction warps, a staged TMA ring, and no cross-CTA global reduction on its ordinary small-batch route. It stores 12-bit base weights with original exception bits. Exception corrections use FP32 arithmetic; preparation rejects unsuitable packing when reconstructed-plus-delta is not exactly the original BF16 weight. QKV also reorders groups of four output rows to distribute exception counts across blocks; the epilogue maps back to original output positions.

This differs from our prior register-decoder modifications and unsuccessful new WGMMA pipeline. It targets M8/16/32 across QKV, pooler, unpooler and O; a broad gain there would matter to multiple load totals. This is a hypothesis to measure, not evidence of superiority.

## Source audit and limits

Parsed the full Python AST without importing and saved the call inventory. No network, credential access, reference/harness imports, process execution calls, output replay or hidden encoded executable source found. File-system queries only locate CUTLASS headers; compilation uses the standard torch load_inline builder. Full upstream prepare has a background CUTLASS build, correctness checks and synthetic-input autotuning. This experiment does not call full prepare or its tuner: it compiles the native extension and invokes only sk2_prepare and _run_sk2 from the lab harness.

The source reads SK2_DELAY_ESC for a debug build option. Its RK router kernel contains globaltimer reads for a two-second deadlock trap. That route is compiled but never invoked in this experiment. It is not a performance-measurement clock, but must not be hidden from an eventual integrity audit. No timing/debug helpers were stripped or disguised. No official candidate has been created yet. A promotion would require a focused self-contained extraction, provenance/license retention, full correctness/nearby-shape review and official integrity checks.

Reviewed SK2 ring lifetime protocol: every correction warp observes every stage and arrives before producer reuse; per-warp FP32 correction buffers are reduced into the final output. Output is allocated fresh for each call. Ordinary weight data determine packing and row balancing, not workload inputs. Review is manual and not a proof of synchronization or numerical correctness.

## First H200 result

All 30 paired comparisons and 40 nearby tests passed, including fresh inputs and retained outputs. A/A ratios 0.98883–1.01054. Batch8 loses. Batch16 QKV improves 2.1%/3.9% in raw speed ratio; O improves 1.5%/1.2%. Batch32 QKV/pooler/unpooler/O improve on both seeds (roughly 2–7%). This is not an aggregate score.

A focused hybrid was generated by tools/build_specialized_candidate.py: only the SK2 dependency closure, six selected configurations and a dedicated extension builder are appended to the unchanged parent. Python globals are namespaced. The unneeded router RK, other GEMM families, CUTLASS build thread and upstream autotuner are not included; their debug and timer code therefore is not in the added portion. This is an ordinary dependency extraction, not hiding an active path. The original protected parent remains byte-identical and retains its previously audited compiler helpers.

The hybrid uses QKV/O for 9–16 tokens and QKV/O/pooler/unpooler for 17–32, covering neighboring shapes rather than scored shapes alone. Unsuitable compression falls back to parent. Source hash 4ee96b46c21a7fe096c456684519b32353ce472a4e369b4aa08023c2bb83f2c9. Full independent-weight testing is required before any official check.

## Full hybrid development confirmation

Exact candidate passed 63 cases per seed (normal/outlier/probe and output lifetime), plus all 30 fresh-input graph checks per seed. Aggregate raw paired ratios versus protected parent: 1.0105203 and 1.0069320; A/A controls: 0.9989997 and 0.9960653. The new extension compiled/prepared in 18.40 seconds after parent was warm; the parent cold preparation was 87.01 seconds. These do not substitute for official cold prepare timing.

Batch32 QKV ratios 1.07117/1.06844, pooler 1.07377/1.05293, unpooler 1.05845/1.03858. O16 did not repeat (1.01136/0.98105); O32 is only 1.00869/1.00463 in full context. This suggests future refinement should focus on the three dominant batch32 layers, not claim every added route is beneficial.

Initial balanced/unbalanced comparisons used changed activations between variants; they are valid comparisons to their paired baseline but are not a controlled causal measurement of row balancing alone. Do not attribute the full architecture gain to balancing.

One official free check requested for the exact unchanged hybrid after these tests. Current account best remains 1.5206695978723808x; its 95% interval is [1.497859553904295,1.5434796418404664]. With only ~1% development gain, overlapping official intervals will be treated conservatively; a slightly higher point estimate alone will not trigger submission.
